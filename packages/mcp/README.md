# mcp

Model Context Protocol `2026-07-28` for constrained Ferrite applications. This source package provides the wire protocol, a stateless client, a resource-server shell, and OAuth 2.1 authorization with no Cargo crate dependency beyond `ferrite-app` (and one source-package dependency, `sha256-hmac`).

## Status

This is a vendored source package targeting protocol revision `2026-07-28`: wire types (`proto.rs`), a stateless client, a resource-server shell, pure-function OAuth 2.1 helpers, base64 encoding, and SHA-256/HMAC re-exports over the `sha256-hmac` source package (which delegates to `ferrite_app::crypto`).

The `2026-07-28` client conformance run covers every `auth/*` scenario scored for that revision (discovery variants, CIMD, dynamic registration, pre-registration, scope selection and step-up, the retry budget, the three token-endpoint auth methods, resource mismatch, offline access, authorization-server migration, and the six `iss` rules), plus the SEP-2243 header, SEP-2322 MRTR, SEP-2575 metadata, and SEP-2106 `$ref` scenarios. For that runner, `2026-07-28` is the draft revision and `2025-11-25` is its latest released revision; at `2025-11-25` this client scores 0 of 18 by design because it has no `initialize` handshake to offer, and that leg is recorded alongside the other. These results measure against the runner's loopback mocks, not against a live authorization server.

Version `1.1.0` fixed four issues found by that run: MRTR retries now carry a fresh JSON-RPC id; `x-mcp-header` parameters are mirrored into `Mcp-Param-*` headers and tools with malformed annotations are excluded (`proto::param_headers`, `proto::validate_tool_header_annotations`, `McpClient::call_tool_declared`); a `-32022` refusal listing a version this client speaks is retried once; and responses framed as `text/event-stream` are parsed (`proto::messages_in_body`).

### The OAuth client half

The OAuth 2.1 client flow (discovery, PKCE, `state`, step-up, and credential keying) is unit-proven and conformance-proven against the official runner's mock authorization server, but remains live-unverified against a real provider. The one live exercise on record was an authorize call that ran RFC 9728 and RFC 8414 discovery against Linear and returned an `https://mcp.linear.app` authorization URL. That is also a dated claim from an isolated sandbox run (`2026-07/08`) with no committed artifact, and it stopped before consent and token exchange.

Completing a live flow against a real provider has one standing configuration requirement: if a provider's authorization server lives on a different origin than its `/mcp` endpoint, that authorization-server origin must also be declared as an egress destination because the platform refuses undeclared hosts. `buzz/ferrite.json` currently declares only the `/mcp` hosts (the Cloudflare set, `mcp.linear.app`, and `api.githubcopilot.com`), so if Linear's or GitHub's AS metadata points off-origin, the token exchange cannot connect until the app spec is edited and redeployed.

## Ferrite Platform Shape

This is a vendored source package, not a Cargo crate and not a service. A consumer mounts it in `ferrite-packages.json` and runs `node tools/ferrite-pkg/ferrite-pkg.mjs sync` to copy the files into its tree. Vendored copies carry `@generated by ferrite-pkg` headers and are never edited in place. All serde usage goes through `ferrite_app::serde` and `ferrite_app::serde_json` with `#[serde(crate = "ferrite_app::serde")]` on derives; everything else relies on `core`, `alloc`, the `sha256-hmac` source-package dependency, and the vendored primitives. There are no external Cargo crates beyond `ferrite-app`, and `hostImports` is empty.

### Why a source package instead of a crate

Other source packages in this repository exist to reconcile code that drifted between apps. This one exists because no external crate can provide MCP to a constrained Ferrite app.

The official Rust SDK (`rmcp`) requires `tokio`, `futures`, and `chrono`. A deployable Ferrite app may depend on only one crate: the platform code gate sets `DEFAULT_ALLOWED_DEPS = &["ferrite-app"]` and matches by dependency name, refusing workspace path dependencies the same way it refuses registry crates. Linking `rmcp` is therefore impossible under the admission gate. That single-dependency rule makes a source package the only mechanism for new shared code as well as reconciling existing copies, as documented in the source-packages guide.

### Boundary and zero host preconditions

Unlike the agent runtime, whose boundary followed measured drift, this package is scoped so a second consumer has nothing to negotiate with its host before mounting it.

- `hostImports` is empty, so nothing in the package reaches back into the host crate.
- SHA-256 and HMAC names live inside the package. Buzz keeps crypto under `relay/crypto/` while the hosted agents app has none, so depending on a host crypto module would have limited this package to one app. Since the workspace split, those wrappers delegate to `ferrite_app::crypto`, replacing roughly 200 lines of duplicated digest code against the relay app with a thin naming surface, `sha256_concat`, and the RFC 4231 test vectors that verify each consumer's SDK build.
- No clock or entropy source is assumed. Time arrives as a parameter and unpredictable values are derived from an injected secret, so no extra capability needs to be wired.

### Platform constraints that shape the design

Two platform limits directly dictate how the protocol and OAuth code work.

`ferrite-app` exposes no RNG, yet a PKCE `code_verifier` still has to be unguessable. The package derives it deterministically as `HMAC-SHA256(secret, label ‖ flow)` under an injected application secret. Security rests on keeping the secret private rather than keeping the derivation secret, and determinism helps on retries: a redelivered request reconstructs the same verifier instead of orphaning an authorization already in flight, which a random verifier would break.

Egress response headers are not exposed. `EgressOutcome::Delivered` carries only `{status, body}`, so the client half cannot read `WWW-Authenticate` on an outbound challenge. The challenge-driven half of RFC 9728 is therefore unavailable to the client, which relies on the specification's own fallbacks: deriving the metadata URL from the resource identifier and using `scopes_supported` for scopes. Per-operation scope hints are unavailable, so `client::ClientError::Forbidden` carries no scope list rather than an invented one. On the server half, `IngressReply.headers` does carry response headers, so hosts can emit `WWW-Authenticate` using `Refusal::challenge`. See the egress response-headers platform request.

## Consuming the package

Add the package to `ferrite-packages.json`:

```json
{ "packages": { "mcp": { "mount": "mcp" } } }
```

Run `node tools/ferrite-pkg/ferrite-pkg.mjs sync`, then declare the module in the crate root:

```rust
mod mcp;
```

Mounting at `mcp` matches the package's own root, so `ferrite-pkg` copies files without path rewrites and the vendored tree stays textually identical to `packages/mcp/src`.

A consumer supplies three runtime inputs:

| Input | Purpose |
| --- | --- |
| HMAC secret | Derives PKCE verifiers, OAuth `state`, and self-issued tokens. |
| Canonical resource identifier | Sets the audience for minted tokens and half of every credential key. |
| Destination-scoped egress handle | Ensures connector hosts absent from the app spec cannot be dialed. |

All three inputs must fail closed. An unconfigured resource identifier must refuse requests rather than taking a value from a request header, which would let a caller choose the audience of tokens issued to it.

## Editing

Edit files under `packages/mcp/src`, then sync vendored copies:

```bash
node tools/ferrite-pkg/ferrite-pkg.mjs sync
```

`ferrite-pkg check` fails if a vendored copy has been edited in place, and the next sync overwrites local edits.

## Not Claimed

| Boundary | Scope and rationale |
| --- | --- |
| Standalone service | This is not an MCP process, deployment, or separate HTTP face, and not a second implementation of an owned capability. It compiles into the mounting app, and every route it serves runs under that app's authority. |
| Earlier protocol revisions | `SERVER_SUPPORTED_VERSIONS` in `proto.rs` is `["2026-07-28"]` only. Clients speaking `2025-06-18` or `2025-11-25` cannot connect because `2026-07-28` is wire-incompatible in both directions and no compatibility shim is provided. Any MCP client that has not adopted `2026-07-28` is excluded. |
| Local JWT signature verification | External JWT-issuing authorization servers are verified through RFC 7662 introspection so the AS response is authoritative and revocation is enforced immediately; this package does not implement local JWKS key fetching/caching or RS256/ES256 JWT validation (even though `ferrite_app::crypto` provides RSA/P-256 primitives for apps that manage their own keys). A deployment configuring an external issuer without introspection should be refused rather than silently trusted. |
| Roots, Sampling, and Logging | Deprecated in protocol revision `2026-07-28`. |
| SSE resumability | Removed from the transport. |
| Storage | `creds.rs` derives keys and structures records; the consuming app performs store I/O through its own handle. |
| Arbitrary runtime URL dialing | The connector catalog is curated because the platform refuses egress destinations without a declared host, which enforces the SSRF boundary. |

## Validation

Because a source package is a module tree rather than a standalone crate, its tests execute inside the apps that mount it:

```bash
node tools/ferrite-pkg/ferrite-pkg.mjs check   # verify vendored copies match this source
cargo test --lib mcp                           # in a consuming app: run the package unit tests and app surface tests
cargo test --test severe_mcp_gate              # in the relay application: test the surface over a real fleet
```

The protocol implementation was also tested against `modelcontextprotocol/conformance` aimed at a deployed app rather than at this source tree. Running against the live wire format caught three gaps that reading the specification missed: SEP-2575's `404` for unimplemented methods, SEP-2243's mirrored `Mcp-Method`/`Mcp-Name` validation, and SEP-2549's caching hints on list results. All three are implemented in `proto.rs` and covered by gate tests in this repository. The recorded conformance score itself is a dated claim; check [Status](#status) before repeating it.

## Events clients

Version `1.4` adds `list_events`, `poll_events`, `subscribe_events`, and `unsubscribe_events` over the existing authenticated transport and mirrored method and name headers. While the ordinary `HttpFetch` interface returns complete response bodies, `EventsStream` in `mcp::events` uses the SDK's incremental POST-stream egress for live consumption. Persist processed event IDs and cursors together, then reopen with the same endpoint, credentials, event, and arguments after a disconnect. Drop both the stream and its egress handle when stopping.

[`browser/events.mjs`](browser/events.mjs) is a separate, dependency-free source module for Node and browser `fetch`. It supports POST streaming with cancellation, heartbeat timeout, and subscription correlation, along with polling and webhook controls. It is not included in the Rust `ferrite add` tree and is not published to npm. See the [guide](https://docs.ferrite.cloud/developers/mcp-events/) and [watch example](https://docs.ferrite.cloud/examples/mcp-events/watch.mjs).

## Publishing a source for an incoming-stream consumer

A separately hosted, app-specific adapter can publish an existing emitting app's polling history as an authenticated MCP POST stream. Several receiving apps can share one source and adapter process using separate capability credentials and durable cursors. The configured source URL is fixed, and event descriptors come from that source. The demo transport uses 64-character hexadecimal capability bearers and one configured webhook callback. A different source requires its own configured instance; multi-source routing and OAuth credential administration are outside that adapter's implemented scope.

A deployed Ferrite app consumes a stream through the existing SDK egress API. Directly publishing a POST stream from a hosted app is not supported by this adapter; use its separately hosted endpoint for the emitting source. See the [incoming-stream guide](https://docs.ferrite.cloud/developers/mcp-events/).

## Using MCP Tasks

Discover `io.modelcontextprotocol/tasks` before calling an asynchronous tool. `McpClient::call_tool_task` may return either a final tool result or a task handle. Persist the handle with the endpoint and account before continuing. After a disconnect, call `get_task` with that handle. Use `update_task` to supply answers to specific outstanding input requests and `cancel_task` to request cancellation.

A cancellation acknowledgement alone does not establish that the worker stopped. Use the final observed state and result to decide what to tell the user. JavaScript applications can use the [Tasks client](browser/tasks.mjs). See the [executable sample](https://docs.ferrite.cloud/examples/mcp-tasks/client.mjs) and the [developer guide](https://docs.ferrite.cloud/developers/mcp-tasks/).
