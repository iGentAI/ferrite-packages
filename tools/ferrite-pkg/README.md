# ferrite-pkg

Source-level package composition for constrained Ferrite apps. It takes one canonical source tree under `packages/<name>/src` and composes it into each consumer's `src/<mount>` with a provenance header, a `crate::<root>` to `crate::<mount>` rewrite, and a SHA-256 lockfile. For the overall model (why source composition exists, what counts as a package, and how to choose boundaries), see the source-packages guide at <https://docs.ferrite.cloud>. This file covers the tool's own contract.

Before committing or preparing a release, run `node tools/ferrite-pkg/ferrite-pkg.mjs verify`. That read-only command checks consumer copies, the registry index, and the MCP package corpus together. Running `check` alone covers consumers and the registry, not the MCP corpus.

When editing a canonical package:

1. Sync in-house consumers.
2. Regenerate the registry.
3. Refresh affected CLI-added consumers with `ferrite add ... --path ... --force`.
4. Regenerate `mcp-packages`.
5. Run `verify`.

Never edit a file whose header says `@generated by ferrite-pkg`: edit the package source and run `sync`. Resolve merge conflicts in a vendored tree by re-running `sync`, never by hand-merging generated copies.

## Commands

```bash
node tools/ferrite-pkg/ferrite-pkg.mjs verify    # check consumers, registry, and MCP corpus (read-only)
node tools/ferrite-pkg/ferrite-pkg.mjs list      # packages, sizes, consumers
node tools/ferrite-pkg/ferrite-pkg.mjs graph     # mounts, host imports, host files
node tools/ferrite-pkg/ferrite-pkg.mjs scan      # cross-crate duplication candidates
node tools/ferrite-pkg/ferrite-pkg.mjs sync      # write copies, prune stale files, refresh the registry
node tools/ferrite-pkg/ferrite-pkg.mjs sync --package <name> [--package <name>]... [app...]
                                                 # only that package: its copies, lockfile entries, registry entry
node tools/ferrite-pkg/ferrite-pkg.mjs check     # verify consumers and registry; exit 1 on drift or orphans
node tools/ferrite-pkg/ferrite-pkg.mjs status    # one line, for CI
node tools/ferrite-pkg/ferrite-pkg.mjs registry  # write packages/registry.json, the index `ferrite add` installs from
node tools/ferrite-pkg/ferrite-pkg.mjs gate [--runner <bin>] [package...]
                                                 # run the platform code gate over packages
node tools/ferrite-pkg/ferrite-pkg.mjs mcp-packages [--check] [--package <name>]...
                                                 # the platform MCP's package corpus
node tools/ferrite-pkg/registry-sign.mjs sign --key <ed25519 PEM> <registry.json>
node tools/ferrite-pkg/registry-sign.mjs verify --trust ed25519:<base64> <registry.json>
                                                 # the index signature `ferrite add` verifies
```

## Syncing one package in a shared checkout

A plain `sync` rewrites every mount of every selected consumer from the working tree. In a checkout shared by multiple sessions, that also copies other sessions' uncommitted package edits into every consumer. On 15 November 2026, a `ferrite-sso` sync wrote a parallel session's Alloy edits into 39 consumers. When changing one package, sync that package alone:

```bash
node tools/ferrite-pkg/ferrite-pkg.mjs sync --package ferrite-sso
```

`sync` prints every path it writes (`+`, `~`) or removes (`-`). Commit only those paths, the changed `ferrite-packages.lock.json` files of the same apps, the package itself, and `packages/registry.json` using `git commit -m "..." -- <paths>`.

`--package` is repeatable. It selects consumers mounting the package (narrowed to any apps named on the command line), writes or prunes files only inside that package's mounts, recomputes only that package's lockfile entries while keeping every other entry byte for byte in its original order, and refreshes only that package's entry in `packages/registry.json`. Before writing anything, it refuses unknown package names and refuses any consumer without a lockfile yet (run a plain `sync <app>` for it first). On an unchanged tree, a scoped sync writes the same bytes as a full sync.

Every `sync`, scoped or full, refreshes `packages/registry.json` when the workspace has one so syncing never leaves the index stale. CLI projects (apps with `vendor/ferrite-app`) are never written by `sync`. When a synced package now differs in such a project, `sync` prints the exact `ferrite add <package> --path <labs> --force` command for that directory and exits 1 so the step cannot be forgotten (the cause of the `demo-member-hub` leftover).

## Generating the MCP package corpus

`mcp-packages` writes `mcp-packages.json`, which contains the packages as the platform MCP serves them to an agent without a shell. Every file matches what `ferrite add <package>` writes at the package root: the provenance header, `#[cfg(test)]` modules stripped by a port of the CLI's `strip_cfg_test_modules`, and each package's README. When a built CLI is present, the test suite compares the port against the real CLI's output for every package. Regenerate the corpus after changing a package; CI and the proof suite run `--check`.

In a shared checkout, `mcp-packages --package <name>` updates only the selected package entries and the registry serial in an existing corpus. Repeat `--package` for multiple packages. Unselected entries remain as published, including entries whose source changed or disappeared. Passing `--check --package <name>` checks that same scope without writing. An initial corpus requires a full generation; unknown names and malformed existing corpora are refused. Unscoped `--check` and `verify` still check the complete corpus and report unrelated drift.

## Signing registry indexes

`registry-sign.mjs` writes and verifies `registry.json.sig`, the detached Ed25519 signature that `ferrite add` requires of any URL registry. It signs `ferrite-registry-index-v1\n` followed by the exact bytes of `registry.json`, formatted as a `{"alg","key_id","signature"}` JSON document. Publish scripts sign the staged index with this tool and refuse to publish without a key. Nothing in this repository holds the private key.

### Signing packages.ferrite.cloud

Every publish of `registry.json` to `https://packages.ferrite.cloud` must be signed with the `ferrite.cloud` registry key:

| Field | Value |
| --- | --- |
| `key_id` | `a2802db62e77cf7a` |
| Public key | `ed25519:Efu7AHD3jlmx6QbnRq3oqOa7HcXV7TUgOyNplBNSG4E=` |
| Private key | GCP Secret Manager, project `ferrite-cloud`, secret `ferrite-cloud-registry-signing-key` |

Every released CLI has this public key built in for `packages.ferrite.cloud` only. It refuses an index signed by any other key, and refuses an unsigned index even with `--allow-unsigned-registry`. Re-sign whenever the index bytes change. The private key must never enter this repository, a sandbox, or a log: read it into a private temporary directory, sign, verify, and delete it.

```bash
KEYDIR=$(mktemp -d); chmod 700 "$KEYDIR"
gcloud secrets versions access latest --project ferrite-cloud \
  --secret ferrite-cloud-registry-signing-key --out-file "$KEYDIR/registry.pem"
node tools/ferrite-pkg/registry-sign.mjs sign --key "$KEYDIR/registry.pem" registry.json
node tools/ferrite-pkg/registry-sign.mjs verify \
  --trust ed25519:Efu7AHD3jlmx6QbnRq3oqOa7HcXV7TUgOyNplBNSG4E= registry.json
rm -rf "$KEYDIR"
```

`sign` must print `key_id a2802db62e77cf7a`. The publish scripts take the same file via `FERRITE_REGISTRY_SIGNING_KEY_FILE` and refuse to publish an index for `ferrite.cloud` that fails verification under this key.

## Status

Active and load-bearing. Every package under `packages/` with a `ferrite-package.json` is composed into the apps that mount it, and `status` prints the current package, consumer, and mount counts. The proof suite runs both gates below in local and full modes, so drift and orphaned mounts fail CI rather than surviving review. `registry` writes `packages/registry.json`, the index `ferrite add` installs from outside this repository.

## Ferrite Platform Shape

Repo tooling, not a Ferrite application: a single-file Node script with no Ferrite routes, bindings, or manifests. It writes only inside consumer `src/` mounts it proves are plain files, refusing symlinks and path traversal through one guarded write choke point. It grants no runtime authority; a composed package executes strictly with the host app's authority.

## Not Claimed

This tool is not a package manager. It fetches nothing, resolves no versions, and generates a registry carrying one version per package for `ferrite add` to install (`version` is a label recorded in the lockfile). It is not a build unit: a package compiles and tests only inside its consumers. It is not for library crates, because the one-dependency rule binds deployable apps only; where Cargo works, use Cargo. `hostFiles` content (the app-owned seam inside a mount) is deliberately unledgered; `scan` reports its drift, but nothing enforces it.

## Validation

```bash
node --test tools/ferrite-pkg/ferrite-pkg.test.mjs   # the tool's own gate
node --test tools/ferrite-pkg/registry-sign.test.mjs # the registry signature
node tools/ferrite-pkg/ferrite-pkg.mjs check         # every copy matches, no orphans
bash tools/ferrite-pkg/consumer-test.sh --out /var/tmp/consumers <app> [<app> ...]
                                                     # the consumers build and pass with the copies they carry
```

`check` proves that vendored copies match their packages. `consumer-test.sh` proves that the apps carrying those copies still build and pass as scratch copies outside the repository workspace beside the packaged SDK twin, matching how a customer checkout resolves them. CI runs both jobs: `vendored-packages` on every push to `main` and every pull request, and `vendored-consumers` when a package, a consumer, the SDK twin, or the script changes. Counts appear in the job summary and cargo logs are saved in the run artifact.

## Password discovery composition

Earlier versions specialized `http-change-password` with the fork's managed-auth password intent through `ferrite auth`, and `check` detected drift in that specialization. That composition was removed with the fork: the package now serves `/.well-known/change-password` for a page the application itself provides (see [its README](../../packages/http-change-password/README.md)), and `sync` composes package bytes only without changing authentication policy or request routes.
